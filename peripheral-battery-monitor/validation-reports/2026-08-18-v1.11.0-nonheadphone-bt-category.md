# Validation Report — v1.11.0 Non-Headphone Bluetooth Battery Category

**Date**: 2026-08-18
**Version**: 1.11.0
**Spec**: `specs/014-bt-input-device-battery.md`
**Scope**: Add a toggleable "non-headphone" Bluetooth device category (input devices, and any non-audio BlueZ `Battery1` device), and fix the headphone classifier that mis-filed audio-capable non-headphones (e.g. an iPad) as headphones.

## Summary

`get_all_batteries()` surfaced `mouse` (Logitech/solaar), `kb` (Keychron/UPower),
and `headphone1`/`headphone2` (BlueZ **audio** devices). Any non-audio Bluetooth
device that reports a battery — a BT mouse/keyboard/trackpad/gamepad/stylus, or a
tablet/phone — had no slot. This change adds `get_bt_devices()` (the non-audio
mirror of `get_headphones()`), emitted as `btdev1`/`btdev2` and selectable in
either top slot via right-click → Devices ("Bluetooth Device" / "Bluetooth Device
(2nd)"), ranked connected-first.

During live testing an iPad appeared in a **headphone** slot at 80%. Root cause:
the `is_audio` test treated any device advertising an A2DP/audio service UUID as a
headphone, and the iPad (BlueZ `Icon 'computer'`) advertises A2DP because it can
source audio to the PC. The discriminator was tightened to use the `Icon`
(`audio-*`) as the signal, with the UUID sniff kept only as a fallback for
devices that expose no icon. The iPad now falls into the non-headphone category.

## Changes

- `battery_reader.py`:
  - Extracted `_enumerate_bt_devices(audio: bool)` from `_enumerate_bt_audio_devices()`
    (now a thin `audio=True` wrapper). `audio=True` returns audio devices (level
    `None` when no `Battery1`); `audio=False` returns non-audio devices that expose
    `Battery1` (devices with no battery are skipped — nothing to show).
  - Tightened the audio discriminator: `icon.startswith('audio-') or (not icon and
    <audio UUID>)` (was `icon.startswith('audio-') or <audio UUID>`).
  - Added `get_bt_devices()` (non-audio, ranked connected-first) and generalized
    `_headphone_rank_key` → `_bt_rank_key` (shared by both readers).
  - `get_all_batteries()` emits `btdev1`/`btdev2`; the `__main__` CLI prints them.
- `peripheral-battery.py`: added two `SLOT_TYPES` rows (`btdev1`/`btdev2`, cache
  `False`). The slot menu, assignment, and `on_data_ready` routing are already
  generic over `SLOT_SPECS`, so no other UI changes were needed.

## Phase 3 — Tests

- `/usr/bin/python3 -m pytest tests/` — **100 passed** (98 prior baseline + new;
  net +7 over the pre-change 93). Stable across runs.
- New tests (`tests/test_battery_logic.py::TestBluetoothDeviceCategory` and a
  `TestSlotConfiguration` addition):
  - `_enumerate_bt_devices(audio=False)` returns connected non-audio devices with
    `Battery1`, excluding audio devices, offline devices, and non-audio devices
    with no battery.
  - `audio=True` unchanged; `_enumerate_bt_audio_devices()` wrapper still works.
  - **iPad case** (mocked dbus, `Icon 'computer'` + A2DP UUID + `Battery1` 80%):
    classified non-audio, surfaced by the non-headphone path, NOT by the headphone
    path.
  - Iconless-audio-UUID fallback still classified as headphone.
  - `get_bt_devices()` surfaces an input device with real name/level; ranking is
    higher-level-first.
  - `get_all_batteries()` emits `btdev1`/`btdev2`.
  - `btdev1`/`btdev2` are valid slot categories and route through `on_data_ready`
    with `use_offline_cache=False`.
- **Integration boundary (BlueZ D-Bus)**: verified against the live daemon.
  `battery_reader.py` CLI after the fix:
  `Mouse: G502 X PLUS 67%` · `Keyboard: Keychron K4 HE (Wired)` ·
  `No headphones connected.` · `BT Device 1: fatpad - 80% (Discharging)` — the
  iPad ("fatpad") moved out of the headphone category into the non-headphone
  category. Before the classifier fix the same probe reported
  `Headphone 1: fatpad - 80%`. The app was bounced on the new build and launches
  cleanly (no errors in the debug log).

## Phase 4 — Code Quality

- The two BlueZ walks (audio / non-audio) were unified into one
  `_enumerate_bt_devices(audio)` rather than copy-pasted; the rank key is shared.
  No dead code introduced. The UI slot machinery was already generic, so the
  category was added by data (two `SLOT_TYPES` rows), not new code paths.

## Phase 5 — Security

- No new dependencies (`dbus` already used). The new code is a read-only BlueZ
  D-Bus enumeration (`GetManagedObjects`, `Battery1.Percentage`); no network,
  subprocess, or user-controlled input. No secrets or credentials touched. Device
  names from BlueZ render through the same existing `setText` path as headphone
  names — no new sink. Dependency CVE scan (pip-audit) not run: no manifest change
  and no tool installed (install requires approval per policy).

## Phase 5.5 — Release Safety

- **Rollback**: revert the commit. Self-contained to `battery_reader.py` (new/
  refactored functions + two `get_all_batteries` keys) and two `SLOT_TYPES` rows.
  No persisted state or config-schema change; unknown slot values already fall back
  to defaults via `_valid_slot`.
- **Behavioral note**: the classifier fix changes which category an audio-capable
  non-headphone (iPad/phone/computer) lands in. A user who had such a device
  pinned to a headphone slot will now see that slot empty (placeholder) unless they
  connect a real headphone or point a slot at "Bluetooth Device". This is the
  intended correction.
