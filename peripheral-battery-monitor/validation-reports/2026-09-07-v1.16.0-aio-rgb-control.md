### A test-isolation bug found and fixed during this work

`test_populated_from_the_profiles_payload` passed alone and failed in the full
suite. `_FakeReply.error()` imported `QNetworkReply` *inside* the method, so in a
full run it resolved to `test_battery_logic`'s collection-time PyQt6 mock and
compared a MagicMock against the real enum, which read as a network error. Fixed
by binding the import at module import time, before that mocking happens.

The investigation surfaced a second, more serious problem: `aio_reader`'s
`DEFAULT_BASE_URL` is bound at its own import, which happens before
`test_aio_section.py` sets `OPENLINKHUB_API`. A section constructed in a test
starts a timer and a `singleShot` poll, so with an event loop turning, tests
could reach the **user's live daemon**. An autouse fixture now pins
`DEFAULT_BASE_URL` to a refusing port for every test in the module. No test in
this project touches real hardware.

## Phase 4 — Code quality

`_iter_devices()` was extracted from `_iter_channels()` in the reader, since RGB
target discovery walks devices rather than channels and both needed the same
pseudo-device skipping. `_build_request()` was extracted in the section, because
the GET poll, the profiles fetch, and the POST writer all need the same timeout
and cache attributes, and three copies would have drifted.

The staged executor carries a generation counter. Without it, two colours picked
in quick succession would interleave: the first sequence's in-flight replies
would advance the second sequence's stage list, dispatching a profile select
before its override. `test_a_newer_request_supersedes_the_tail_of_an_older_one`
covers it.

No unused imports. No method over 50 lines. `_build_aio_rgb_menu` is the longest
addition at 42 lines and is flat declarative menu construction.

## Phase 5 — Security review

**Verdict: CONCERNS** — the same pre-existing system-package CVEs, plus a new
write surface that was reviewed specifically.

- **Phase A (CVE scan)**: `pip-audit` under `/usr/bin/python3`, re-run.
  `Found 26 known vulnerabilities in 2 packages` — unchanged: `aiohttp` 3.13.3
  and `msgpack` 1.1.2, neither imported in this sub-project, both system pacman
  packages.
- **Phase B (OWASP, AI-assisted, best-effort, not compliance evidence)**:
  clean, with the write path reviewed directly.
  - **Injection**: no user input reaches a URL. Every request path is a module
    constant (`color/setOverride`, `color`, `brightness`); the base URL is
    `DEFAULT_BASE_URL`. User-supplied values appear only as JSON *body* values
    through `json.dumps`, which escapes them.
  - **Input validation**: colours pass through `parse_color`, which returns
    either a triple of ints bounded 0–255 by two-hex-digit parsing or `None`.
    Brightness is range-checked 0–3 and raises otherwise. Effect names in the
    menu come from the daemon's own per-device list.
  - **SSRF**: unchanged from 017. The endpoint is `127.0.0.1:27003` unless the
    operator overrides `OPENLINKHUB_API` in their own environment.
  - **Access control**: the API is unauthenticated on localhost. Any process on
    this machine could already issue these writes; the monitor adds no exposure
    that did not exist.
  - **Logging**: colour, effect, brightness, and every failed or rejected write
    are logged. No credentials exist on this path to leak.
- **Phase C (secrets)**: 0 findings, inline scan.
- **Phase D (supply chain / agent config)**: clean. No dependency manifest,
  lockfile, or agent-config path in the diff.

### The deliberate write boundary

017 AC18 forbade all writes; 019 AC12 replaces it with a speed-write guard,
asserted over all three AIO modules. Grep across `aio_reader.py`,
`aio_color.py`, `aio_section.py`, and `peripheral-battery.py` for `/api/speed`,
`/api/psu/speed`, `/api/temperatures/new`, `/api/temperatures/update`,
`/api/temperatures/updateGraph`, and `setSpeed`: no matches. The reason is not
caution about hardware but honesty — this firmware accepts duty writes and
discards them, so a speed control would report success and change nothing.

## Phase 5.5 — Release safety

- **Rollback**: revert the commit. No config key, no persisted app state, no new
  dependency.
- **What a rollback does not undo**: RGB state already written to the device.
  Unlike everything else in this project, these writes outlive the process —
  OpenLinkHub stores the override in `database/profiles/<serial>.json`. A colour
  set from the menu survives a revert, an app restart, and a reboot. Change it
  back from the menu, `sysadmin/scripts/aio-color.sh`, or the OpenLinkHub WebUI.
- **Blast radius**: writes are user-initiated from a menu only. Nothing on a
  timer, at startup, or on recovery writes anything. A device with no RGB
  channels gets no menu.
- **Brightness side effect**: applying a colour at brightness 0 also sets
  brightness to 100%, and that persists. It is the only case where the monitor
  changes a setting the user did not directly pick, and it applies only where
  every LED is already dark.
- **No install or uninstall changes.**

## Known limitations

- **Colour changes are persistent and survive a code rollback.** See release
  safety above.
- **No live colour readback in the UI.** The menu sets state; it does not show
  which colour or effect is currently active. `aio-color.sh --status` still does
  that.
- **All RGB channels are written together.** Per-channel control, which the API
  supports, is not exposed. Nothing in the menu can light one fan differently
  from the rest.
- **One device only.** The cooler, or the first RGB device if no cooler is
  present. The script's `--all` mode, which also covers a mousepad or other
  peripherals, has no equivalent here.
- **No colour picker.** `Custom…` takes a hex string; `QColorDialog` is a heavy
  modal for a frameless always-on-top widget.
- Effects that need the override disabled are handled, but an effect's own
  speed and colour parameters are not exposed.
