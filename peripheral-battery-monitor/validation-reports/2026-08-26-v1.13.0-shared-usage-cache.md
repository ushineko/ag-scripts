# Validation Report — v1.13.0 Shared usage cache for the Claude section

**Date**: 2026-08-26
**Scope**: `usage_cache.py` (mirrored in), `peripheral-battery.py`;
companion change in `claude-usage-widget-windows` v3.4.0

## Executive Summary

The Claude section polled `/api/oauth/usage` directly on its own timer, while
the `claude-usage-widget` terminal panes coordinated through a shared cache.
Total request volume therefore scaled with the number of watchers times the
number of accounts. Adding a second account doubled this widget's share to
60 requests/hour on its own. The widget now reads through the same per-account
gate as the panes, so the whole machine makes ~1 request per account per
window regardless of how many things are watching. Reviewers should look first
at the injection seam in `usage_cache.fetch_usage_cached` (the fetch function
is now a parameter, which is what lets one file serve both layouts) and at
`UpdateThread.run`.

## Motivation — measured, not assumed

| Source | Before | Cache |
|--------|--------|-------|
| GUI widget | 2 accounts × every 2 min = **60/hr** | none |
| 4 live `--tui` panes | ~1 per account per window, total | shared |

Two rate-limit events were observed during development. Both were
*near-simultaneous calls on the same token* — first two calls a second apart
while both stores held duplicate credentials, then a probe process racing the
running widget — not sustained volume. Concurrent processes on one account are
the trigger, which is exactly what a shared gate plus lock removes.

## Phase 4 — Code Quality

- `usage_cache.py` became import-free of project-local modules: the fetcher is
  injected and `get_cache_dir()` moved into the module. That is what makes it
  mirrorable verbatim, joining `usage_shape.py` and `accounts.py` under the
  same convention. `config.get_cache_dir()` now delegates, so there is one
  definition rather than two that could drift apart — and drift here would
  silently mean two caches and no sharing at all.
- No duplicated cache logic: the GUI gained a call site, not an implementation.
- `UpdateThread` gained explicit `usage_ttl` / `force_usage` constructor
  arguments rather than reading globals.

## Phase 5 — Security Review

- **Dependencies**: unchanged; nothing added.
- **Secrets**: the cache stores usage payloads and timestamps only — no
  credentials. That property is unchanged and was re-checked: the widget passes
  a `store_dir` and a fetch function, never a token, into the cache layer.
- **Cache file permissions**: files are created under the user cache dir with
  default permissions and hold no sensitive data. Credential files remain
  `0600` and are untouched by this change.
- **Path traversal**: account names still pass through `_slug()` before
  becoming filenames.
- **New shared-state risk considered**: two projects now read and write the
  same files. Writes are atomic (tmp + `os.replace`) and guarded by a
  non-blocking `flock` that auto-releases on process death, so a crashed widget
  cannot wedge the panes. A corrupt or partial file is treated as no cache.

## Phase 5.5 — Release Safety

- **Rollback**: revert the commit and relaunch. The widget returns to direct
  polling; the cache files are simply left unread. No migration, no state to
  unwind, and the companion project keeps working either way.
- **Additive**: `fetch_usage_cached`'s new parameters both default to previous
  behavior.
- **Failure mode is conservative**: if the cache directory is unwritable the
  lock degrades to gate-only coordination and fetches still happen; the widget
  does not break, it just loses the sharing benefit.

## Acceptance

Widget restarted; it created the shared per-account cache files itself
(`usage-max.json`, `usage-work.json` under `~/.cache/claude-usage-widget/`),
which is the proof it is reading through the shared layer rather than polling
directly.

**Note on the restart**: the per-account cache files were deleted immediately
before the restart, so the widget and all four live panes saw an empty cache
and raced for the same accounts at once — the exact herd the gate exists to
prevent. One account recorded a failed fetch as a result. This was an artifact
of clearing the cache by hand, not of the change; the lock and gate handle the
steady state, and the failure path behaved correctly (gate pushed out, no
last-known-good clobbered).

## Defects found during acceptance (both fixed here)

1. **Stacked throttles deadlocked an account.** Putting the cache gate in front
   of the existing internal usage-API backoff meant the inner throttle returned
   `rate_limited` without making a request, the cache recorded that as a failed
   fetch and pushed its gate out again, and the two re-armed each other. A
   direct call to the same account succeeded while the cached path stayed
   stuck. Fixed by making the cache the single throttle
   (`use_usage_backoff=False` on that path) and propagating `retry_after` so it
   honors the server's own window.
2. **A cache miss displayed as "not logged in".** The stuck gate returned a
   null reading, which the TUI rendered as a logged-out account — libelling a
   healthy, freshly-authenticated login. Null now renders as `no reading yet`
   when the credential file is present, and "not logged in" only when it is
   genuinely absent.

Both have regression tests. The first was only visible because the throttles
interacted under a real 429; neither would have been caught by the unit tests
written before acceptance.
